01

全体像

Spring Boot(Java 21) + Thymeleaf + MySQL で作られた投資信託の注文アプリ。ORM は使わず、JdbcTemplateで素のSQLを書くスタイル。Controller → Service → Repository → DB という素直な3層構成に、画面間でデータを運ぶInvestmentTrustFormが1つ通っている。

パッケージ構成(com.example.internship)

controller/ … HTTPエンドポイント(1ファイルに集約)
entity/     … 画面間データ(Form)とDB1行を表すクラス群
repository/ … JdbcTemplateでのSQL実行
service/    … 手数料計算・約定日計算などのビジネスロジック

画面は顧客向け4枚(紹介・入力・確認・完了)、行員向け2枚(ログイン・一覧)の計6枚。金融機関・支店・銘柄はinstitution_master / branch_master / fund_masterというマスタテーブルにコードで持たせ、注文データ(investmentTrust_table)側は名称ではなくコードだけを保存する設計になっている。

行員モードの認証まわり

@Value("${investment-trust.staff.id}")
private String staffId;
@Value("${investment-trust.staff.password}")
private String staffPassword;

// staffId・staffPasswordの両方が一致したときだけセッションに認証済みフラグを立てる
if (staffId.equals(id) && staffPassword.equals(password)) {
    session.setAttribute("staffAuthenticated", true);
    return "redirect:/investmentTrust/staff";
}

Spring Securityは使わず、HttpSessionに真偽値を1つ立てるだけの軽量な実装。staffList()の冒頭でこのフラグを確認し、なければ/investmentTrust/staff/loginへリダイレクトする。ID/パスワードはapplication.ymlの固定値。

名称解決のprivateメソッド

resolveInstitutionName / resolveBranchName / resolveFundName は、確認画面表示のために コード→名称 を引く。裏側はマスタRepositoryのfindAll()を都度呼んでJavaのStreamで絞り込んでいる(データ件数が小さい前提のシンプルな実装)。

04

Entity / Form

entity/配下は5クラス。役割は「画面間を流れる書き込み用データ」「マスタ1行」「一覧表示専用の読み取りデータ」の3種類に分かれる。

InvestmentTrustForm — 画面間を流れるメインのデータ

フィールド由来
institutionCode / branchCode / bankAccountNum / bankSubject口座情報セクションの入力値
lastName / firstName / address / contactお客様情報セクションの入力値
fundCode / purchaseAmount注文内容セクションの入力値
purchaseFee / orderDatetime / tradeDateユーザー入力ではなくサーバーが計算して埋める値。確認画面・完了画面へ運ぶための「入れ物」も兼ねている

Lombokの@Dataで全フィールドのgetter/setterを自動生成。@NonNullはユーザー入力必須項目に付けてあるが、これはあくまで「Lombokが生成するsetterにnullチェックを足す」だけの効果で、フォームバリデーションの主役はHTML側のrequired属性。

InvestmentTrustOrderView — 行員一覧専用の読み取りDTO

行員モード一覧で表示する1行分を表す。InvestmentTrustFormと似ているが、コードではなく解決済みの名称(institutionName, branchName, fundName)を持つ点が違う。書き込み(Form)と読み取り(OrderView)でクラスを分けているのは、両者の形が本質的に異なる(名称解決の有無)ため。

InstitutionMaster / BranchMaster / FundMaster — マスタEntity

institution_master・branch_master・fund_masterの1行にそのまま対応する素朴なクラス。FundMasterだけpurchaseFeeRate(BigDecimal)を持ち、手数料計算の元になる。

05

Repository

repository/配下は4クラス。すべてJdbcTemplateを直接使い、SQL文字列を自前で組み立てるスタイルで統一されている。

InvestmentTrustRepository

create() — 1件の注文をinvestmentTrust_tableにINSERTする。カラム名はInvestmentTrustFormのフィールド名と1対1で対応させてあり、位置引数のズレによるバグを起こしにくくしてある。

SELECT im.institution_name, bm.branch_name, ...
FROM investmentTrust_table t
JOIN institution_master im ON im.institution_code = t.institution_code
JOIN branch_master bm ON bm.institution_code = t.institution_code
                       AND bm.branch_code = t.branch_code
JOIN fund_master fm ON fm.fund_code = t.fund_code
ORDER BY t.order_datetime DESC

findAllOrders() — 行員モード一覧用。3マスタとJOINしてコードを名称に変換した状態で、新しい注文から順に返す。

InstitutionMasterRepository / BranchMasterRepository / FundMasterRepository

それぞれ対応するマスタテーブルのfindAll()を持つ。FundMasterRepositoryだけfindByCode(fundCode)も持ち、手数料計算(OrderInvestmentTrustService)と名称解決(Controller)の両方から使われる。

06

Service

ビジネスロジックを担当する2クラス。どちらもDBやWeb層に直接依存しない範囲を意識して切り出してある。

OrderInvestmentTrustService

// 円未満切り捨て
BigDecimal fee = fundMaster.getPurchaseFeeRate()
        .multiply(BigDecimal.valueOf(purchaseAmount))
        .setScale(0, RoundingMode.DOWN);

resolvePurchaseFee()が手数料計算の本体。orderInvestmentTrust()はこれを呼んだうえでTradeDateCalculatorで約定日を確定させ、最後にInvestmentTrustRepository.create()を呼んでDB保存する — つまり「確定処理の入り口」としてこの2つを1メソッドにまとめている。

TradeDateCalculator

calculate(orderDatetime):
    if 土日: return 次の月曜日
    if 時刻 < 15:00: return 当日
    else: return 翌営業日(土日はスキップ)

締切時刻(平日15:00)を基準に約定日を1日ずらすロジック。祝日カレンダーは持たないため、平日判定はisBusinessDay()で「土日でないこと」のみをチェックしている。DB・Web層への依存が一切ないので、単体テストが書きやすい形になっている。

07

画面(テンプレート)

templates/配下は6枚。Thymeleafのレイアウト機能(fragment)は使わず、各画面が<style>込みで完結した1ファイルになっている。

ファイル内容
investmentTrustIntro.html紹介ページ。ヒーロー+特徴4カード+実データの取扱ラインナップ表+CTAボタン
investmentTrustMain.html入力画面。「お客様情報」「口座情報」「注文内容」の3セクション(.form-section)構成
investmentTrustConfirmation.html確認画面。金額の内訳表示、hiddenフィールドでコードを次画面へ引き継ぐ
investmentTrustCompletion.html完了画面。注文日時・約定日を表示
investmentTrustStaffLogin.html行員ログイン画面。ID/パスワード+パスワード表示切替
investmentTrustStaffList.html行員一覧画面。全注文をテーブル表示

入力画面の3セクション構成

すべて元から用意されていたが未使用だった.form-section/.section-titleのCSSを使って、フィールドを意味のあるグループに分けている。

セクションフィールド
お客様情報姓・名・住所・連絡先
口座情報金融機関名・口座番号・支店名・科目名
注文内容銘柄選択・購入金額・購入手数料(見込み)

支店の動的絞り込み(institutionCode → branchCode)

支店selectは初期状態で空。金融機関を選ぶと、Thymeleafが埋め込んだbranchMasterList(JSON)をJSがフィルタして、その金融機関に属する支店だけを動的に追加する。

確認画面の金額内訳

「注文金額(10,000円) ＝ 投資される金額(9,670円) ＋ 手数料(330円)」という式をそのままHTMLに表現。investedAmount(投資される金額)はControllerが購入金額 − 手数料で計算してModelに積んでいる。手数料が0円の場合はth:unlessで分岐し「購入手数料 0円（無料）」と表示する。

ステップ表示(シェブロン型)

入力・確認・完了の3画面共通で、CSSのclip-pathを使った矢印形のセグメントを表示。.chevron.active(現在地・青)、.chevron.done(完了済み・緑)、無指定(未実施・グレー)の3状態を各画面で静的に切り替えている(JSではなく画面ごとにHTMLをハードコード)。

08

JavaScript

static/js/配下は2ファイル。どちらもフレームワークを使わない素のDOM操作。

investmentTrust.js(入力画面)

  • 支店の絞り込み — populateBranchOptions()
  • 手数料プレビュー — updateFeePreview()。銘柄・金額の変更のたびに概算を再計算(最終確定は必ずサーバー側で再計算するため、ここはあくまでUX目的)
  • 購入金額のカンマ整形 — formatWithCommas() / parseAmount()。表示はカンマ付き、送信直前にparseAmount()でカンマを外した数値へ戻す
  • 口座番号の整形 — 数字以外を除去して7桁に切り捨て、フォーカスが外れたら7桁未満を先頭0埋め
  • 入力済みチェックマーク — requiredFieldIds配列に載っている全項目を対象に、入力/選択されたら「※」を隠して「✓」を表示するupdateFieldCheck()
  • リセット時の再同期 — formのresetイベント後、setTimeoutで1tick待ってから支店選択肢・手数料プレビュー・チェックマークを未入力状態に戻す(ブラウザのネイティブresetは値のクリアが先、イベント発火はその後という順序に依存)
  • 高額注文の確認ダイアログ — 送信時、金額が100万円以上ならconfirm()で最終確認

investmentTrustConfirmation.js(確認画面)

「申し込む」ボタン押下時に、画面に表示されている科目名・銘柄名・購入金額をtextContentから読み取って確認ダイアログの文言を組み立てる。購入金額はカンマ付き表示のため、replace(/[^0-9]/g, "")で数字だけを取り出してからNumber()に渡している。

09

DBスキーマ

db/schema_v2.sql に定義。自動マイグレーションの仕組みは組んでおらず、手動実行が前提。

テーブル役割主なカラム
institution_master金融機関マスタinstitution_code(PK), institution_name
branch_master支店マスタ(金融機関に従属)institution_code+branch_code(複合PK), branch_name
fund_master銘柄マスタfund_code(PK), fund_name, purchase_fee_rate
investmentTrust_table注文データ本体id(PK), institution_code, branch_code, bank_account_num, bank_subject, last_name, first_name, address, contact, fund_code, purchase_amount, purchase_fee, order_datetime, trade_date
補足

investmentTrust_tableは(institution_code, branch_code)でbranch_masterへ、fund_codeでfund_masterへ外部キー制約を張っている。bank_account_numは先頭0を保持するためVARCHAR(7)(Integerではない)。last_name/first_nameは元々1つのpurchaser_name列だったものを分割した経緯があり、address/contactとあわせて後からALTER TABLEで追加している。

11

既知の制約・今後の課題

  • 顧客マスタがない — 姓名・住所・連絡先は注文ごとの自由入力で、同一人物かどうかを判定する仕組みは持たない。顧客ID管理は将来対応として先送りされている
  • 祝日カレンダー非対応 — TradeDateCalculatorは土日のみをスキップし、祝日は平日として扱う
  • 行員モード認証はセッションベースの簡易実装 — Spring Securityは未導入。単一の固定ID/パスワードのみで、複数アカウントやロール管理はできない
  • schema_v2.sqlはDROP前提 — 冒頭で既存テーブルをDROP TABLEするため、新規構築用のスクリプトとしては使えるが、稼働中のDBに直接流すと過去データが消える(稼働中DBへの追加変更は個別にALTER TABLEを実行してきた)
